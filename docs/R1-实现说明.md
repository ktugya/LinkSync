# LinkSync R1 实现说明

本文记录 **实际交付的 R1 版本** 的实现方式、接口与取舍。它与 `docs/实现方案-v2.md`（带 TLS / 配对 / 分块续传的设计）不是同一套东西：按你的要求，R1 以“最短时间做出来、局域网内不要安全”为前提，砍掉了加密、配对、鉴权、断点续传。

## 0. 1.1 增补

- **二维码**：PC 用共享 UI 的 `qrcode.min.js` 生成 `linksync://add?ip=...&port=...`；Android 用 `zxing-android-embedded` 的 `IntentIntegrator` 扫码，解析后 `Net.fetchInfo` + `Store.touchPeer`，复用“手动添加”链路。PC 无摄像头，因此只显示不扫描。
- **LS 图标**：`scripts/make-icons.py` 用 Pillow 生成 Windows 多尺寸 `.ico`、Android 自适应图标前景/背景与旧版 mipmap、`favicon.svg`。
- **PC 原生窗口**：`MainForm` 承载 WebView2，关闭隐藏到托盘；单实例通过命名事件 `LinkSync.PC.Activate` 唤醒已运行窗口，而不是再开浏览器。
- **安装包**：Inno Setup，按用户安装到 `%LOCALAPPDATA%\Programs\LinkSync`，可选桌面/开机自启，内置 WebView2 引导程序（仅在缺失时运行）。
- Android 端因此启用 AndroidX（`android.useAndroidX=true`），APK 约 5.9 MB。

## 1. 目标与前提

- 设备：Windows PC + Android 手机/平板，最多 4 台。
- 网络：同一局域网；不做公网、中继、NAT 穿透。
- 安全：**不做 TLS、不做配对、不做鉴权**；同一网段内能访问端口即可读写。仅在可信网络使用。
- 优先级：能跑、好用、开发快；后台常驻尽量稳。

## 2. 总体结构

每个设备都是对等节点，同时运行：

1. **HTTP 服务**（0.0.0.0:47821，占用则顺延）：
   - 提供本机 Web UI（PC 由 Kestrel 提供，Android 由 NanoHTTPD 从 assets 提供）；
   - 提供被其他设备调用的 REST API。
2. **UDP 广播发现**（47822）：每 3 秒广播 `{id,name,platform,port}`，同时监听；收到后记录来源 IP。
3. **UI**：PC 用系统浏览器打开 `http://127.0.0.1:47821`；Android 用 WebView 打开同一地址。两端共用 `shared/www`。
4. **本地状态**：内存列表（对端、传输、剪贴板、消息）；PC 持久化设置到 `%LOCALAPPDATA%\LinkSync\settings.json`，Android 用 SharedPreferences。

```
┌──────────── PC ────────────┐        ┌────────── Android ──────────┐
│ WinForms 托盘               │        │ MainActivity + WebView       │
│ Kestrel :47821 + wwwroot    │◄──────►│ NanoHTTPD :47821 + assets    │
│ UDP 发现 / 剪贴板轮询        │  HTTP  │ SyncService（前台服务）       │
│ SQLite? 否，内存 + settings  │  UDP   │ UDP 发现 / 剪贴板 / 传输      │
└─────────────────────────────┘        └──────────────────────────────┘
```

### 为什么用 Web UI

- 一套 HTML/CSS/JS 同时服务 PC 浏览器和 Android WebView，省掉 WPF XAML 与 Compose 两套界面。
- 安卓端的文件选择、剪贴板读写通过 `@JavascriptInterface` 桥接给原生，避免 WebView 直接处理大文件。
- PC 端不需要主窗口，浏览器只是“界面”，关掉浏览器服务仍在托盘运行。

## 3. API

所有接口都是 JSON（上传除外），无鉴权。端口以实际监听为准。

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/info` | 本机 `{id,name,platform,port,version}` |
| GET | `/api/state` | UI 所需的全部状态（自身、对端、传输、剪贴板、消息、设置） |
| GET | `/api/health` | 存活探测 |
| POST | `/api/clipboard` | 其他设备推送剪贴板 `{text,hash,origin,originName,ts}`，本机写入剪贴板 |
| POST | `/api/text` | 其他设备推送文本消息 `{id,from,fromName,text,ts}`，Android 弹通知 |
| POST | `/api/text/send` | UI 发文本 `{to:[id],text}`，本机负责投递/排队 |
| POST | `/api/upload` | 接收文件；头部 `X-File-Name`、`X-File-Size`、`X-From-Id`、`X-From-Name`，body 为原始字节 |
| POST | `/api/send?peer=<id>` | PC UI 选文件后上传到本机，本机再转发给目标 |
| POST | `/api/peers/add` | 手动添加 `{addr:"ip:port"}` |
| POST | `/api/settings` | 修改名称、自动剪贴板等 |
| POST | `/api/local/clipboard` | PC：读取本机剪贴板并广播 |
| POST | `/api/local/copy` | 把指定文本写入本机剪贴板 |
| POST | `/api/transfers/clear` | 清空已完成传输 |

### 状态结构（节选）

```json
{
  "self": {"id":"...","name":"PC","platform":"windows","port":47821},
  "peers": [{"id":"...","name":"手机","platform":"android","ip":"192.168.1.5","port":47821,"online":true}],
  "transfers": [{"id":"...","peerName":"手机","direction":"out","name":"a.zip","size":123,"bytes":60,"status":"running"}],
  "clipboard": [{"id":"...","text":"...","fromName":"PC","ts":1790000000000}],
  "messages": [{"id":"...","text":"...","fromName":"手机","ts":1790000000000}],
  "settings": {"name":"PC","autoClipboard":true,"downloadDir":"...","startWithWindows":false,"port":47821}
}
```

## 4. 关键流程

### 发现与在线

- 收到 UDP 包即 `touchPeer`，`lastSeen` 更新；`now - lastSeen < 15s` 视为在线。
- 每 6 秒对“超过 8 秒没更新”的对端调用 `GET /api/info` 兜底（手动添加、广播被防火墙拦截时仍能保持在线）。
- 对端 IP 变化时以最新 UDP 来源为准。

### 剪贴板

- PC：WinForms Timer 每 500 ms 读一次剪贴板；内容变化且不是刚应用过的远端内容 → 写入历史 → 向所有在线对端 `POST /api/clipboard`。
- Android：Activity 在前台时每 800 ms 读一次；变化则调用 Service 广播；Service 收到远端推送时直接 `setPrimaryClip`。
- 回环抑制：`Store.lastAppliedText/At` + 本机 `lastClip`，收到后不再二次广播。
- Android 后台无法读剪贴板（系统限制）：通知按钮/网页按钮会打开 Activity，取得焦点后再读。

### 文本

- 发送端写入本地历史，逐个对端 `POST /api/text`；失败的进入内存队列，每 5 秒重试。
- 接收端按消息 `id` 去重；Android 发通知（Action“复制”），PC 弹托盘气泡。

### 文件

- PC 发送：浏览器把文件 PUT 到本机 `/api/send?peer=`，Kestrel 用 `HttpClient` 流式转发到对端 `/api/upload`，`ProgressStream` 统计字节。
- Android 发送：JS 调用 `AndroidBridge.pickFiles(peerId)`，原生打开 SAF 选择器，Service 用 OkHttp 流式上传到对端 `/api/upload`。
- 接收：PC 写 `Downloads\LinkSync\<发送方>\<文件名>`；Android 写 MediaStore `Download/LinkSync`（`IS_PENDING`）。
- 传输中持有 `PARTIAL_WAKE_LOCK`（Android）或 `SetThreadExecutionState`（PC），结束后释放。
- R1 不做断点续传；大文件靠流式，不占内存。

## 5. Android 后台常驻

- `SyncService`：`connectedDevice` 类型前台服务，`START_STICKY`、`stopWithTask=false`。
- 服务内同时持有：NanoHTTPD 服务器、UDP 发现、消息重试、在线状态巡检。
- 常驻通知：显示在线设备数、Action“发送剪贴板”。
- 开机自启：`BootReceiver` 监听 `BOOT_COMPLETED` / `MY_PACKAGE_REPLACED`。
- 任务划掉：`onTaskRemoved` 用 `AlarmManager` 尝试 1.5 秒后重启。
- 电池白名单：设置页一键跳 `ACTION_REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`。
- 注意：Android 15 对 `dataSync` 前台服务有 6 小时/24 小时限制，所以这里刻意用 `connectedDevice`。

## 6. 与 v2 方案的差异

| 项 | v2 设计 | R1 实际 |
|---|---|---|
| 安全 | TLS + 证书固定 + 双向 Token + 配对 | 全部去掉 |
| 配对 | 二维码 / SAS | 无需配对，自动信任 |
| 文件 | 1 MiB 分块 + 断点续传 | 单次流式上传，无续传 |
| Android 服务端 | Ktor | NanoHTTPD |
| UI | WPF + Compose | 共用 Web UI（浏览器 / WebView） |
| 发现 | mDNS + UDP | UDP 广播 + 手动 IP |
| 消息 | WebSocket 长连接 | UI 轮询 `/api/state`（800 ms） |

轮询而不是 WebSocket 的原因：实现简单、断线自动恢复、无需维护长连接；4 台设备下开销可忽略，代价是 UI 刷新最多延迟 0.8 秒。

## 7. 已验证 / 未验证

已在 Windows 上验证：

- PC 服务启动、静态 UI、`/api/state`、`/api/info`；
- 模拟对端（Node 脚本）完成文本收发、文件双向传输（1 MB）、剪贴板双向同步、在线状态保活；
- 浏览器截图检查布局；
- 单文件自包含 exe 启动；
- APK 编译成功、`aapt` 校验权限/入口、`lint` 0 error、debug 签名有效。

未验证：

- Android 真机/模拟器运行（开发环境无可用设备，WSA 因虚拟化未启用无法启动）。
- Android ROM 的后台保活、MediaStore 写入、WebView 桥接等需要在真机上确认。

## 8. 后续可加（按优先级）

1. 文件名/MIME、断点续传、多文件进度。
2. Android 分享菜单（`ACTION_SEND`）直接发文件/文本。
3. 设备组/二维码配对（如果以后要重新加安全）。
4. 图片剪贴板、文件夹传输。
5. 传输加密（若离开可信局域网）。
